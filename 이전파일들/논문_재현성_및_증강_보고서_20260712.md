# Velocity Augmentation and Reproduction Audit

Date: 2026-07-12

## Implemented Training Augmentations

The following changes are deliberately limited to the training input path.
Evaluation, validation rollout, checkpoint loading, and boundary clamping use
clean deterministic inputs exactly as before.

`gnn_surrogate/model.py` now exposes `augment_training_inputs(...)`. It
returns a small `TrainingAugmentation` object containing `current_u`,
`prev_u`, and `inflow_context`, so `scripts/train.py` only passes a coherent
input bundle to the feature builder. There is no noise branch in evaluate.py.

The selectable methods are:

| Number | Method | Exact behavior |
| --- | --- | --- |
| `1` | Temporal noise | Perturbs both `u(t)` and `u(t-1)` with correlated Gaussian fields. With correlation `rho`, each field is `sqrt(rho) * shared + sqrt(1-rho) * innovation`. Therefore the acceleration feature is also perturbed through the difference of the two fields. |
| `2` | Spatially smooth noise | Replaces independent node noise with graph-neighborhood averaging over mesh edges. Fixed wall/inlet nodes are reset to zero after every smoothing round, and dynamic-node RMS is restored per velocity component. |
| `3` | Magnitude jitter | Multiplies `u(t)`, `u(t-1)`, and the global inflow context by one positive sample-wide factor. Wall/inlet velocity values remain exact. |

For methods `1` or `2`, inflow context receives one shared three-component
Gaussian perturbation for every node. This keeps it a global inlet feature,
rather than turning it into unrelated node-wise noise. Inflow speed statistics
are clamped at zero after perturbation because mean/min/max speed cannot be
negative.

The local acceleration is not perturbed through a second, unrelated noise
source. It is recomputed from the two perturbed velocity inputs. This avoids
an inconsistent triple `(current velocity, previous velocity, acceleration)`.
At the default correlation `0.8`, it still has nonzero perturbation because
the two innovation fields differ. Setting correlation to `1.0` makes the
additive part of the acceleration perturbation vanish.

## New Arguments

| Argument | Default | Meaning |
| --- | ---: | --- |
| `--velocity-augmentations 1 2 3` | `1 2 3` | Selects the numbered methods above. Use `1`, `1 2`, or `1 2 3` for controlled ablation. Passing the flag with no number disables all three. |
| `--noise-std` | `0.003` | Additive noise amplitude in units of the training velocity standard deviation. Used by methods `1` and `2`. |
| `--temporal-noise-correlation` | `0.8` | Correlation between the additive noise on `u(t)` and `u(t-1)`. Must be in `[0, 1]`. |
| `--spatial-noise-smoothing-steps` | `2` | Number of graph-neighborhood averaging rounds for method `2`. |
| `--magnitude-jitter-std` | `0.02` | Standard deviation of the global multiplicative factor used by method `3`. |

Recommended first ablation, while keeping every other argument identical:

```bash
# A: temporal consistency only
--velocity-augmentations 1

# B: temporal plus spatially smooth noise
--velocity-augmentations 1 2

# C: full augmentation
--velocity-augmentations 1 2 3
```

Use the same `seed`, split, and 50-step validation selection for all three.
Compare their final unseen-test 50-RMSE only after selecting the winning
configuration on the 10 validation cases.

## Paper-Faithful Defaults Corrected

The paper describes the decoder as predicting a velocity update, local
acceleration as a velocity difference between consecutive input steps, and
the convection term as `u dot grad(u)` (Methods, pp. 11-13). New training
runs therefore now default to:

```text
--output-scale acceleration
--acceleration-mode acceleration
--physics-operator gradient
```

Older checkpoints remain compatible: evaluation reads their saved arguments.

## Remaining Reproduction Gaps

The source code is not public, so the items below are classified by what the
paper establishes versus what is unavailable in the released HDF5 data.

| Priority | Gap | Why it matters | Current status / action |
| --- | --- | --- | --- |
| High | Exact inlet/outlet labels | The paper fixes a known parabolic inlet profile. The HDF5 files do not expose inlet/outlet masks, so this project infers caps geometrically and chooses inlet from mean flow direction. A wrong cap directly corrupts every rollout step. | Validate `scripts/inspect_boundaries.py` on representative cases. Prefer mesh/XDMF metadata or author-provided labels if available. |
| High | Test protocol differs from Table 1 | The paper reports 95 train / 10 test cases. This project intentionally uses 90 train / 10 validation / 5 unseen test. A 5-case unseen-test RMSE is useful, but it is not numerically comparable with the published 10-case table. | Keep the three-way split for model selection. Run a separate frozen 95/10 protocol only for a table-to-paper comparison. |
| High | Future inlet information is read from the HDF5 target frame | `inflow_context` and inlet clamping use `target_u` on the inferred inlet cap. This is valid only because the paper assumes the future prescribed inlet waveform is known. It is not a free-running surrogate that predicts an unknown inlet. | For deployment, supply the waveform/profile from a separate boundary-condition input rather than a future CFD file. |
| High | Physics operator is still an approximation | The paper evaluates finite-difference operators over mesh neighborhoods. The new `gradient` mode is structurally closer than legacy mode, but the exact solver-side discretization, viscosity handling, and loss scaling are unpublished. | Use `gradient`; treat physics weights as a tuned approximation, not an exact reproduction. |
| Medium | Exact noise process is unspecified | The paper states that noise is added to all dynamical variables, but does not give its distribution, correlation, magnitude, or whether it includes known inlet context. | The new implementation follows the stated scope while exposing every material choice as an argument. It is a faithful interpretation, not a claim of identical code. |
| Medium | Normalization is unpublished | The paper lists features but does not specify velocity/update/position normalization. This project uses training-set vector statistics for velocity and update outputs, per-case position scaling, and edge-length scaling. | Preserve normalization files with every run. Do not claim an exact normalization match without author code/details. |
| Medium | Strong reproducibility is not enabled | Seeds are set, but CUDA scatter/index-add operations and GPU libraries can still be non-bitwise-deterministic. This explains different runs with identical arguments without implying checkpoint resume. | Record run metadata and add a deterministic-mode audit before interpreting a single run as decisive. |
| Check | Velocity unit label | `rmse_mm_s` reports the raw HDF5 velocity unit and does not multiply by 1000. The local dataset symlink was unavailable during this audit, so the HDF5 unit could not be independently confirmed here. | On the server, inspect a velocity magnitude and file metadata before calling the value mm/s in a paper comparison. |

## Items That Already Match the Paper Direction

- MLPs use two hidden layers of 128 ReLU units, latent size 128, and 15
  message-passing rounds.
- Node features include velocity, position, time, one-hot node type, local
  acceleration, and global inlet mean/min/max speed for In-MGN variants.
- Edge features are relative position plus Euclidean distance.
- Wall velocity is fixed to zero; inlet is fixed; wall and inlet are excluded
  from the learning loss while outlet nodes remain learned.
- Whole-geometry and fluid-only metrics are both reported. The former is the
  appropriate counterpart to Table 1.
- The best checkpoint can be selected using validation 50-RMSE, rather than
  only a one-step error.
